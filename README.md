# tinylm: a small language model built from scratch

A GPT-style language model and a BPE tokenizer, written from scratch in PyTorch to learn how they work.
No pretrained models, no pretrained tokenizers, no nanoGPT-style template. Every piece has comments
explaining what it does and why.

This is milestone 1: tokenizer, data pipeline, model, training loop, sampling, tests and a Colab notebook.

## Repo layout

```
README.md
requirements.txt
configs/            model size and training settings (JSON): smoke, tiny (~2M), small (~11M), medium (~20M)
tinylm/

  bpe.py            byte-level BPE tokenizer: training, encode, decode, save/load
  data.py           dataset checks, download, tokenization, token files, batch sampler
  prepare_data.py   CLI: python -m tinylm.prepare_data
  model.py          the transformer (RMSNorm, RoPE, attention, SwiGLU, weight tying)
  train.py          training loop, LR schedule, validation, checkpoints, resume (CLI)
  sample.py         temperature / top-k generation (CLI)
  chat.py           interactive multi-turn chat (CLI)
  eval_chat.py      run a fixed prompt list on a saved model and write the transcript (CLI)
  smoke.py          end-to-end CPU smoke test (CLI)
  logutil.py        console + file logging and JSON-lines metrics
tests/              pytest: tokenizer, data, model, training/resume (all offline)
notebooks/
  colab_train.ipynb the Colab training notebook (generated by build_notebook.py)
  colab_chat.ipynb  chat with / evaluate an already trained model, no GPU needed (build_chat_notebook.py)
reports/
  REPORT.md         per-model performance report (living document), transcripts/, scores/, score_summary.py
```

## Quick start

Local CPU check (needs internet for the dataset download, about 10 MB):

```bash
pip install -r requirements.txt
python -m pytest -q tests          # unit tests, no network
python -m tinylm.smoke             # real data subset, 20 training steps, resume, sampling
```

Real run (this is what the notebook does):

```bash
python -m tinylm.prepare_data --data_dir data --vocab_size 2000
python -m tinylm.train --config configs/tiny.json --data_dir data --out_dir runs/tiny
python -m tinylm.sample --ckpt_dir runs/tiny --prompt "Once upon a time"
python -m tinylm.sample --ckpt_dir runs/tiny --chat --prompt "Hi, how are you?"
python -m tinylm.chat --ckpt_dir runs/tiny      # interactive multi-turn chat
```

Any setting can be overridden on the command line without editing files, for example
`--set train.max_steps=2000 model.n_layer=6`.

## Colab (free T4), from a phone

1. Open `notebooks/colab_train.ipynb` in Colab (GitHub > open in Colab, or upload it).
2. Runtime > Change runtime type > T4 GPU.
3. Edit the settings cell if needed (`CONFIG`, `BRANCH`), then Runtime > Run all.
4. Allow the Google Drive prompt. Data, checkpoints and logs go to `MyDrive/tinylm/`.

If the session disconnects: reconnect and Run all again. Data preparation is skipped (already on
Drive) and training resumes from the newest checkpoint. If the repo is private, add a Colab secret
named `GITHUB_TOKEN`.

What you get on Drive:

```
MyDrive/tinylm/data_v2000/        token files, tokenizer.json, meta.json, prepare.log
MyDrive/tinylm/runs/tiny/
    ckpt_latest.pt                model + optimizer + step; used for resume (ckpt_prev.pt is the one before)
    ckpt_best.pt                  model weights at the best validation loss
    train.log                     everything printed during training (appended across resumes)
    metrics.jsonl                 loss, lr, grad norm, throughput, validation, one JSON per line
    tokenizer.json                copy of the tokenizer, so the run folder is self-contained
```

## Using a model you already trained

Checkpoints stay on your Drive in `MyDrive/tinylm/runs/<config>_<chat mode>/` (the very first run is
`runs/tiny`). Nothing needs retraining. Open `notebooks/colab_chat.ipynb` in Colab (a CPU runtime is fine), set
`RUN` to the folder name, and run the cells: mount Drive, list your models, chat, or run the standard
question list (`python -m tinylm.eval_chat --ckpt_dir <run folder>`). The run folder also holds `train.log` and
`metrics.jsonl`.

## Model sizes

Size is entirely a config setting. Parameter count is printed when training starts.

| config | layers | dim | heads | context | vocab | parameters |
|--------|--------|-----|-------|---------|-------|------------|
| smoke  | 2      | 64  | 2     | 64      | 512   | 0.14M (CPU test only) |
| tiny   | 4      | 192 | 6     | 256     | 2000  | 2.16M |
| small  | 6      | 384 | 6     | 256     | 2000  | 11.4M |
| medium | 6      | 512 | 8     | 256     | 2000  | 20.0M |

The vocab size must match the tokenizer; training stops with a clear message if it does not. To use a
different vocab size, run `prepare_data --vocab_size N` and set the same N in the config.
The training numbers (learning rate, steps, batch size) are reasonable starting points, not tuned.

## How it works

### Tokenizer (`bpe.py`)

Byte-level BPE. The base vocabulary is the 256 bytes, so any text is representable and decoding is
lossless. Training counts how often each adjacent pair of tokens occurs, merges the most frequent
pair into a new token, and repeats until the vocabulary has the requested size (default 2000, of
which 5 are special tokens). The ordered merge list is the whole tokenizer. Text is first split into
word-like pre-tokens by a regex, and merges never cross those boundaries. Special tokens are only
emitted when explicitly allowed, so dataset text can never inject them.

### Data (`data.py`, `persona.py`, `prepare_data.py`)

* Stories: `roneneldan/TinyStories` (parquet, column `text`).
* Chat source: `HuggingFaceTB/smoltalk`, subset `everyday-conversations` (parquet, column `messages`, a list
  of `{role, content}` with roles `user` and `assistant`).

Five chat modes (`prepare_data --chat_mode`):

* `persona`: chat data written from the Petryk bank in `persona.py` only (about 25 kinds of exchange: greeting,
  who are you, what can you do, limits, feelings, compliments, jokes, moods, simple context, and so on), with two
  real parts: "tell me a story" replies are real short TinyStories, and questions the bot cannot answer are real
  user messages from everyday-conversations, always answered with an honest "I do not know that". Petryk is a
  calm, plain-spoken small language model that is honest about its limits. Validation uses held-out phrasings.
* `dailydialog_identity`: real DailyDialog dialogues plus a small identity layer (default 1,500 conversations,
  about 3% of chat tokens): the Petryk bank restricted to identity, limits, politeness, simple context, stories and
  honest "I do not know" replies. The layer is mixed into training only; validation stays DailyDialog-only, so the
  validation loss is directly comparable with a `dailydialog_only` run. `identity_examples.txt` in the data folder
  shows what was added. It is ordinary training data, not a rule: the model learns it like everything else.
* `dailydialog`: only real, human-written dialogue, nothing authored. It combines DailyDialog (about 13k
  everyday dialogues, read from the Hub's parquet conversion of `roskoN/dailydialog`; each dialogue is
  also used with its first utterance dropped so the bot side learns from both speakers) with
  everyday-conversations. Text is cleaned (pre-tokenized spacing, curly quotes). Check the DailyDialog
  license before reuse; I believe it is non-commercial. In a short CPU test the replies were fluent,
  short and human-sounding but mostly off-topic; a 2M model cannot hold a real conversation.
* `dailydialog_only`: DailyDialog alone. The two datasets above have different voices (an LLM-written helpful
  assistant vs. two people chatting), which gave inconsistent replies, so this keeps a single style.
* `real`: the everyday-conversations data as published.

In both modes the chat loss is computed on the bot's words only (`train.chat_loss = "bot_only"`).

Before relying on them, the script asks the Hub that the datasets and expected files exist, and
checks the columns and roles when reading (it raises with a clear message otherwise). Findings used
by the code: the chat data has no system messages, always starts with a user turn and alternates
turns; some conversations end with an unanswered user turn, which are dropped so every conversation
ends with a bot reply. No persona or system prompt is added.

Chat format (role names are mapped to `<|user|>` and `<|bot|>`; a turn ends with `<|end|>`):

```
<|user|>Hi there<|end|><|bot|>Hello! How can I help you today?<|end|><|user|>...<|end|><|bot|>...<|end|><|endoftext|>
```

Stories are the plain text followed by `<|endoftext|>`. Everything is stored as flat `uint16` token
files and read through `np.memmap`. Each training example is a random window of `context_len + 1`
tokens; inputs are the first `context_len` tokens and targets are the same window shifted by one.
Each batch mixes stories and chat according to `chat_fraction`. Batches are a pure function of
(seed, step), so a resumed run continues on exactly the data it would have seen.

### Model (`model.py`)

A decoder-only transformer. Token embeddings go through N blocks, then a final norm and an output
layer that shares its weights with the embedding. Each block is
`x = x + Attention(norm(x))` then `x = x + MLP(norm(x))`.

* Attention: every token builds a query, key and value; the weights are `softmax(q.k / sqrt(d))`
  over earlier tokens only (causal mask); the output is the weighted sum of values. Heads run in
  parallel on slices of the channels. `attn_impl: "manual"` is the explicit version of the math;
  `"sdpa"` (default) uses PyTorch's fused kernel. A test checks they agree.
* RoPE: positions are encoded by rotating queries and keys, so attention depends on relative distance.
* RMSNorm and a SwiGLU MLP: standard modern choices.
* Weight tying: saves `vocab * dim` parameters, which is a large share at 2M.

### Training (`train.py`)

AdamW (weight decay on matrices only), linear warmup then cosine decay of the learning rate,
gradient clipping, mixed precision (fp16 with loss scaling on the T4, fp32 on CPU), gradient
accumulation for larger effective batches. Validation uses a fixed set of batches, so the numbers are
comparable across steps, and is reported separately for stories and chat.

Checkpoints are written to a temp file and renamed (so a crash cannot corrupt them), and the previous
one is kept as a fallback. Resume restores model, optimizer, loss-scaler and step. Resuming with a
different model config is refused.

### Early stopping and repetition control

* **Early stopping** (`train.early_stop_patience`, default 3): after each validation run the mixed validation loss
  is compared with the best so far; after 3 validations in a row without a new best, training stops, saves its
  state and prints `EARLY STOP`. The best checkpoint (`ckpt_best.pt`) is the one to use. The counter is stored in
  the checkpoint, so a Colab disconnect does not reset it, and re-running a stopped run does nothing. Set
  `train.early_stop_patience=0` to turn it off or to keep training a stopped run.
* **Repetition penalty** (`--repetition_penalty` in `sample`, `chat` and `eval_chat`): tokens already used become
  less likely (a positive logit is divided by the penalty, a negative one multiplied by it). In chat it covers the
  words of the bot's own earlier replies and the reply being written; the end-of-reply token is never penalized.
  Defaults: 1.2 in `chat` and `eval_chat`, 1.0 (off) in `sample`. In a quick test on a weak CPU model 1.2 broke an
  identical-reply loop and 1.4 also made replies drift, so treat the value as something to tune per model, for
  example `python -m tinylm.eval_chat --ckpt_dir <run> --repetition_penalty 1.0` and then `1.1`, `1.2`, `1.3`
  (each writes its own transcript file).

### Sampling (`sample.py`)

Logits are divided by the temperature, cut to the top-k, turned into probabilities and sampled.
Temperature 0 is greedy. `--chat` wraps the prompt as `<|user|>...<|end|><|bot|>` and stops at `<|end|>`.

## What the logs tell you

At start: environment and GPU, the full config, token counts per file, tokens per step, how many
passes over each dataset the plan makes, the exact parameter count, and a decoded example of the first
training batch (to see the data pipeline is right).

Things that indicate a healthy run:

* `initial val loss` is close to `ln(vocab)` (7.60 for 2000). A warning is printed if it is not.
* Training loss falls steadily; `grad_norm` is mostly below the clip value (1.0) after warmup.
* `skipped` stays near zero (fp16 overflow steps skipped by the loss scaler; a few early on are normal).
* Validation loss for stories and chat both fall. If chat validation rises while chat training keeps
  falling, the model is memorizing the small chat set: lower `chat_fraction` or train fewer steps.
* The sample text at each EVAL line goes from noise, to word-like fragments, to sentences.

## Known limits and notes

* The real everyday-conversations set is small (about 2,200 conversations, 570k tokens) and broad, so
  a 2M model trained on it only invents topical nonsense. That is why the `persona` mode exists.
  The persona bot is deliberately narrow: it will chat, tell stories and jokes, and admit it is small,
  but it knows very little. That is what makes tiny models feel coherent.
* Persona data is hand-written and template-expanded, so it is not a 'download from Hugging Face' dataset.
  Edit `tinylm/persona.py` to change the voice: replies and phrasings are plain lists.
* Because validation phrasings are held out, but replies are shared, chat validation loss is optimistic.
  The real test is chatting with it.
* Sampling has no KV cache (it recomputes the window each token); fine at this size.
* Both datasets have their own licenses; see their Hugging Face dataset cards before reusing the data.
* The prepare script disables the Hugging Face "Xet" download backend (`HF_HUB_DISABLE_XET=1`) because it
  needs extra hosts that restricted networks block, and the plain download is fast enough.
